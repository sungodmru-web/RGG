CODE PACK 8 — SECURE RGG PUBLISHING DASHBOARD

Implement ONLY Code Pack 8.

OBJECTIVE:

Create a protected administrative publishing interface for RGG Research & Insights.

The final workflow must allow an authorized administrator to:

- list publications;
- create a publication;
- save a draft;
- edit a publication;
- publish a publication;
- archive a publication;
- delete a publication with confirmation;
- open the public version when published.

==================================================
0. PACK 7 PREREQUISITE
==================================================

Before changing code, verify that Code Pack 7 publication persistence/API exists.

Confirm:
- database publication model exists;
- API publication endpoints exist;
- publication records persist in PostgreSQL;
- public research API returns published records;
- draft/published/archive status exists or can be directly mapped.

If Pack 7 is NOT present:

STOP.

Do not implement a fake CMS.
Do not use localStorage.
Do not use a static TypeScript array.

Report:

"Code Pack 8 requires Code Pack 7 database/API."

==================================================
1. REUSE EXISTING API
==================================================

Inspect the exact publication API created in Code Pack 7.

Reuse:
- existing API clients when available;
- existing schemas;
- existing validation;
- existing types where practical.

Do not create duplicate incompatible publication models.

The supplied Pack 8 types/API client are target patterns only.

Adapt them to Pack 7 where necessary.

==================================================
2. SECURITY
==================================================

Admin protection must be server-backed.

Do NOT secure /admin using:
- query parameters;
- URL secrecy;
- localStorage boolean;
- JavaScript-only password;
- hard-coded frontend secret.

All write operations must be protected server-side.

Protect:
POST publication
PATCH publication
DELETE publication

Administrative reads that expose drafts/archived records must also require authorization.

Public publication API must continue returning published content only.

If the project already has authentication:
reuse it.

If the project has no authentication:
implement the smallest secure server-backed admin session appropriate to the existing Express architecture.

Do not introduce OAuth/social login unless already configured.

Do not expose credentials in frontend source.
